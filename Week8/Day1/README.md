# Day 1 — Enable Logging & Diagnose N+1 (CardioTrack)

## Overview
Enabled EF Core query logging, seeded the database with a realistic data 
volume, and analyzed the actual SQL query count generated by the three 
most important list endpoints to check for N+1 query problems.

## Sprint 3 Goal
Diagnose and document genuine N+1 query problems across CardioTrack's 
primary list endpoints under realistic data volume, targeting constant 
query count (O(1)) regardless of result size — incorporating the Sprint 2 
retrospective action of writing authorization edge-case tests before 
extending any endpoint touched this sprint.

## Steps Completed

-  Enabled EF Core query logging in development via `LogTo()` and 
      `EnableSensitiveDataLogging()`, printing every generated SQL query 
      to the console.
-  Seeded the database with 55 patients, 150 vital signs, and 60 
      appointments to simulate realistic data volume.
-  Ran the 3 most important list endpoints and counted actual queries 
      generated for each, using the console log as the source of truth.
-  Documented findings, including one real performance issue found.

## Endpoints Tested

| Endpoint | Queries Generated | Notes |
|---|---|---|
| `GET /api/Doctor/get-patients` | 1 | Direct projection, no related data loaded |
| `GET /api/Doctor/doctor-view-vitalsignalert` | 1 | Uses `.Include(p => p.Patient)` correctly |
| `GET /api/DoctorAndNurse/get-appointments-by-status-to-nurse` | 1 | Query count is fine, but see finding below |

## Finding
No genuine N+1 problem (i.e., 1 query becoming N queries as result size 
grows) was found in the three endpoints tested — each generates a constant 
number of queries regardless of result count.

However, `GetAppointmentToNurseAsync` includes `.Include(d => d.Doctor)` 
even though the response DTO (`AppointmentDto`) never uses any Doctor 
field — meaning the query fetches unnecessary related data on every call. 
Not an N+1 issue, but a real over-fetching problem worth fixing.
